## Defect report
- Title: Excluding all three tools makes POST /api/pizza answer 500 with an empty body
- Request: `POST https://quickpizza.grafana.com/api/pizza` with the header `Authorization: token <token of a logged-in user>` and the body `{"excludedTools": ["Knife", "Pizza cutter", "Scissors"]}`. With curl: `curl -i -H "@auth.txt" -d "@all_tools.json" https://quickpizza.grafana.com/api/pizza`
- Expected result: status 400 and a JSON error message saying that no pizza can satisfy the restrictions (product owner rule: never 500).
- Actual result: `HTTP/1.1 500 Internal Server Error`, `Content-Length: 0`, empty body.
- Severity: Medium. Only one unusual input triggers it and the other requests keep working. But the server fails without a message, so a client cannot tell the user what went wrong, and a 500 suggests an unhandled error in the server code.

## Part B
1. The tests can find failures that only show up when the real parts work together. One is a configuration or deployment problem, such as the load balancer sending requests to servers that do not share users (Step 0.12). Another is a fault in how the parts interact, such as a wrong status code, a mistake in JSON serialisation, or a database that does not store or return the data correctly. A stub only returns what we told it to, so it would hide all of these. Unit tests with stubs are still worth writing because they are fast and deterministic and do not need the network. When one fails, it points straight to the function at fault, and it can easily test edge cases that are hard to set up through the API.
2. With the public token, every student shares the same ratings, so another person could change or delete a rating while my test is running, and my test would fail for no reason or damage someone else's data. A new user per test keeps every test isolated and independent of order. In Project 2, each test will create its own data (for example its own customer, cart or booking with a unique generated name), use only that data, and delete it in the fixture teardown. It will never touch the data of other groups.
3. QuickPizza runs on several servers behind a load balancer, and each server keeps its own users. A `requests.Session` keeps the `AWSALB` cookie, so every request in the run goes to the same server, and the user we created is still there when we log in and rate. In my three runs of Step 0.12 without a session, 1 passed and 2 failed with 401 on the login. The result depended on luck, so the test was flaky.
4. The block "all three tools are excluded" revealed the defect. A 500 with an empty body tells the client nothing. The app cannot tell whether its input was wrong or the server crashed, so it cannot show a useful message, and it might retry a request that will never work. A 400 with a message says the input cannot be satisfied and why. The test stays as `xfail` so that the known defect stays visible in every run and in the report. With `strict=True`, the run fails as soon as QuickPizza fixes it, which reminds us to remove the mark. If we deleted the test, we would lose that check and forget about the defect.
5. Base choice: 1 base test plus (number of blocks - 1) for each characteristic = 1 + (3-1) + (4-1) + (2-1) + (3-1) = 1 + 2 + 3 + 1 + 2 = 9 tests. All combinations: 3 x 4 x 2 x 3 = 72 tests.
6. Read: 404, change: 400, delete: 400. All are refused and the rating stays unchanged, so access control works. I would expect the same code for all three: either 404 Not Found for each (which does not reveal that the rating exists) or 403 Forbidden for each. A 400 Bad Request is wrong for change and delete, because the request itself is well formed. The problem is ownership, not the input. This is a minor defect in consistency and correctness of status codes, not a security defect, since no data is leaked or changed. A client that relies on the status code could still handle it wrongly.
7. The response is 200 with a list of ratings that belong to other users (for example `{"id":1,"stars":5,"pizza_id":1}, ...`). A made-up 16-character token is accepted as valid. This is a defect (broken authentication): the server seems to check only the length of the token, not whether it was ever issued. On a real system, a stranger could guess any token of the right length and read other people's data, or with write access even change or delete it, without ever logging in.
8. An API test checks the business rules and the exact responses better: status codes, error messages, every field of the JSON, and inputs that the web pages would never send (decimals, text, missing fields, other users' ids). It also runs faster and more reliably than a browser test. Only a test through the web pages can check what the user actually sees and does: the layout, that buttons and forms work, that messages are shown on the screen, and that the JavaScript in the browser calls the API correctly.
